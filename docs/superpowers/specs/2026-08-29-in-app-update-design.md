# 时间规划局应用内更新设计

## 目标

为“时间规划局”增加完全免费的应用内更新能力。App 使用公开 GitHub Releases 检查和下载新版 APK，用户无需 GitHub 账号、会员或网盘页面。更新必须使用相同包名和签名覆盖安装，并通过数据库迁移保留现有记录和设置。

## 已确认决策

- 更新托管：公开 GitHub Releases。
- GitHub 仓库：只公开 APK 和更新说明，不公开 App 源代码。
- 建议仓库名：`time-planning-updates`。
- 检查方式：启动时每天自动检查一次，并在“我的”页面提供手动检查。
- 更新方式：可选更新，用户可以“立即更新”或“以后再说”。
- 下载方式：用户确认后直接下载 APK，不跳转会员、广告或网盘页面。
- 远端信息来源：GitHub Releases API 的 latest release。
- 固定附件名称：`time-planning.apk`。
- 当前签名继续作为永久更新签名，防止手机中的现有记录因无法覆盖安装而受影响。

## 版本约定

首个带应用内更新功能的版本为：

- `versionName = "1.1.0"`
- `versionCode = 2`
- GitHub Release 标签：`v1.1.0`
- APK 附件名称：`time-planning.apk`

后续每次发布必须同时满足：

- `versionCode` 严格递增。
- `versionName` 使用三段式版本号，例如 `1.2.0`。
- Release 标签等于 `v` 加 `versionName`。
- Release 中只有一个名为 `time-planning.apk` 的 Android 安装包。

App 使用 Release 标签中的语义版本与本机 `versionName` 比较。无法解析的标签视为无效更新，不提示安装。

## 首次启用更新

当前手机中的 `1.0` 不包含更新检查代码，因此它不能自行发现或下载 `1.1.0`。首次启用需要执行一次引导覆盖安装：

1. 使用当前永久签名构建包含更新器的引导 APK，保持 `versionCode = 1`、`versionName = "1.0"`。
2. 连接保存现有记录的手机，先核对已安装 APK 与引导 APK 的证书指纹一致。
3. 使用覆盖安装方式安装引导 APK，不卸载旧 App、不清除数据。
4. 发布正式 `v1.1.0` Release。
5. 从引导版 App 内检查、下载并安装 `1.1.0`，完成第一次真实应用内更新验证。

正式源码和发布配置最终保留 `versionCode = 2`、`versionName = "1.1.0"`。引导 APK 只用于这一次迁移，不上传为正式 Release。

## GitHub 更新源

App 请求公开仓库的 latest release 接口，读取：

- Release 标签作为远端版本号。
- Release 正文作为更新说明。
- `time-planning.apk` 资源的下载地址、文件大小和 SHA-256 digest。

只有同时满足以下条件时才显示更新：

- Release 不是草稿。
- Release 不是预发布版本。
- 标签可解析为三段式版本号。
- 远端版本高于本机版本。
- 存在且仅存在一个指定名称的 APK 附件。
- 附件提供可识别的 SHA-256 digest。

网络访问使用系统 HTTPS。App 不内置 GitHub Token，也不向用户索取 GitHub 登录信息。

## 检查策略

### 自动检查

- App 启动后读取上次成功检查时间。
- 距离上次成功检查不足 24 小时时不发起请求。
- 超过 24 小时则在后台检查一次。
- 自动检查无更新或网络失败时不弹出提示。
- 用户选择“以后再说”后，当天不再自动提示同一版本；24 小时后可再次提示。

### 手动检查

- “我的”页面提供“检查更新”。
- 手动检查不受 24 小时间隔限制。
- 检查过程中显示加载状态，避免重复请求。
- 已是最新版时明确提示当前版本已是最新。
- 网络、响应格式或服务错误时显示可理解的错误信息，并允许重试。

检查时间、当天忽略的版本和下载任务状态使用 SharedPreferences 保存，不写入 Room 业务数据库。

## 用户界面

“我的”页面增加“软件更新”区域，显示：

- 当前版本号。
- 当前更新状态。
- “检查更新”按钮。

发现新版后显示可选更新弹窗：

- 新版本号。
- Release 更新说明。
- APK 文件大小。
- “立即更新”。
- “以后再说”。

用户点击“立即更新”后进入下载状态：

- App 页面显示下载状态和进度。
- Android 系统通知显示下载进度。
- 下载失败后显示“重新下载”。
- 不在用户确认前自动下载 APK。

## 下载与安装

下载由 Android DownloadManager 执行，目标文件放在 App 可管理的下载位置。每个新任务开始前清理该 App 之前未完成或已失效的更新 APK，避免安装旧文件。

下载完成后按顺序执行：

1. 计算本地文件 SHA-256，并与 GitHub Release asset digest 比较。
2. 使用 PackageManager 读取下载 APK 的包信息。
3. 确认包名等于 `com.example.birthdaycountdown`。
4. 确认 APK 的签名证书 SHA-256 等于当前 App 的签名证书 SHA-256。
5. 确认 APK 的 `versionCode` 高于当前安装版本。
6. 所有校验通过后才调起 Android 系统安装确认页。

任意校验失败时：

- 删除下载文件。
- 清除下载任务状态。
- 显示具体失败原因。
- 不启动安装流程。

首次安装外部 APK 时，如果 App 没有“允许安装未知应用”权限，先打开系统授权页。用户返回后再次检查权限，授权成功则继续安装；用户拒绝则保留更新提示但不反复弹窗。

普通 App 不执行静默安装，最终安装必须由 Android 系统页面让用户确认。

## 签名与记录保护

当前 Debug APK 和本机签名文件已经核对为同一证书：

- 现有签名文件：`C:\Users\杨\.android\debug.keystore`
- 证书 SHA-256：`6BAE13563A55D51BCCDC76F15DCAE27D6F9C6A531624BF8CFD9D5883162C2B52`

实施时将当前签名复制为独立的永久更新密钥：

```text
C:\Users\杨\.time-planning\time-planning-release.keystore
```

同时在 `D:\时间规划局密钥备份\time-planning-release.keystore` 创建第二份本机备份。首次发布前提示用户再将该备份复制到 U 盘或其他离线存储，并确认文件可以读取。签名文件、密码、GitHub 登录凭证和本机配置文件不得进入公开更新仓库。

Release 构建显式使用永久更新密钥。首次发布前，需要连接保存现有记录的手机，读取已安装 App 的证书指纹并与上述指纹比较。指纹不一致时停止发布和安装，不允许通过卸载旧 App 解决。

## 数据库安全

- 移除 Room 的 `fallbackToDestructiveMigration()`。
- 保留现有数据库版本 1 到 8 的显式迁移。
- 以后每次数据库结构变化都必须增加明确迁移和迁移测试。
- 缺少迁移时允许 App 启动失败并报告问题，不允许自动删除数据库。
- 包名固定为 `com.example.birthdaycountdown`，不得为更新功能改包名。
- 覆盖安装只更新程序文件，Room 数据库和 SharedPreferences 继续保留。

应用内更新不代替记录备份。记录导出与导入可以作为后续独立功能，本轮不扩大范围实现。

## 发布工具

增加本机发布脚本：

```text
tools/publish-update.ps1
```

脚本接受版本号和更新说明文件，发布前执行：

1. 检查 GitHub CLI 已登录目标账号。
2. 检查公开仓库 `time-planning-updates` 存在。
3. 检查 `versionName` 与目标 Release 标签一致。
4. 检查 `versionCode` 高于上一版本。
5. 使用永久更新签名构建 Release APK。
6. 检查 APK 包名、版本号和签名指纹。
7. 计算并输出 APK SHA-256。
8. 创建 GitHub Release 并上传为 `time-planning.apk`。
9. 重新读取 Release API，确认远端版本、附件名称、大小和 digest 正确。

任何检查失败时脚本立即停止，不创建不完整 Release。脚本不得保存 GitHub Token 或将密钥复制进项目目录。

## GitHub 首次配置

用户需要亲自完成：

- 注册 GitHub 账号。
- 邮箱验证和人机验证。
- 在本机授权 GitHub CLI 登录。

完成登录后可由本机工具协助：

- 创建公开仓库 `time-planning-updates`。
- 添加简短说明，注明仓库只用于“时间规划局”安装包更新。
- 创建第一个 `v1.1.0` Release。

## 组件边界

- `UpdateChecker`：请求 GitHub、解析 Release、比较版本。
- `UpdatePreferences`：保存检查时间、忽略版本和下载状态。
- `UpdateDownloader`：启动和观察 DownloadManager 任务。
- `ApkVerifier`：校验 digest、包名、版本号和签名。
- `UpdateInstaller`：处理未知来源权限并调起系统安装页。
- Compose 更新界面：展示状态、弹窗、进度和错误，不直接处理网络或文件校验。
- 发布脚本：只负责构建、校验和上传，不参与 App 运行时逻辑。

这些组件通过明确数据类型传递状态，避免将更新网络、下载和安装逻辑堆入现有页面文件。

## 错误处理

- 无网络：自动检查静默结束；手动检查提示网络不可用。
- GitHub 超时或限流：保留当前版本，提示稍后重试。
- Release 格式错误：视为无可用更新并记录诊断信息。
- 下载取消或失败：清理任务并允许重试。
- SHA-256 不一致：删除 APK，提示文件校验失败。
- 包名或签名不一致：删除 APK，提示安装包不是可信更新。
- 安装权限被拒绝：不循环打开设置，允许用户稍后重试。
- 系统安装被取消：保留当前 App 和全部记录，不重复自动安装。

## 验证标准

- 当前版本为 `1.1.0`、`versionCode = 2`。
- App 每 24 小时最多自动检查一次，手动检查不受限制。
- 无新版、网络失败和无效 Release 不触发自动打扰。
- 正确 Release 能显示版本、说明、大小并下载指定 APK。
- 下载进度可见，失败后可重试。
- 修改 APK 内容后 SHA-256 校验失败且不会安装。
- 使用不同包名或不同签名的 APK 时校验失败且不会安装。
- 未授权未知来源安装时正确引导到系统设置。
- 取消更新或取消系统安装不会影响现有记录。
- 从数据库版本 8 覆盖安装到新版本后，卡片、排序、颜色、导航设置均保留。
- `fallbackToDestructiveMigration()` 已移除。
- Release 发布脚本能在上传前后验证包名、版本、签名和 digest。
- Debug/Release Kotlin 编译成功，单元测试源码编译成功，Release APK 构建成功。
- 在真实手机上完成一次从当前已安装版本到 `1.1.0` 的覆盖更新验证。
- 在真实手机上先覆盖安装同版本引导 APK，再通过 App 内更新从引导版升级到正式 `1.1.0`，全程不得卸载或清除数据。

## 范围限制

- 本轮不实现静默安装或后台强制安装。
- 本轮不实现强制更新。
- 本轮不公开源代码。
- 本轮不增加账号系统、云同步或记录导入导出。
- 本轮不支持 Google Play In-App Updates。
- 本轮不支持私有 GitHub 仓库或 App 内 GitHub 登录。
